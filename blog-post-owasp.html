What the OWASP Top 10 2026 Changes Mean for Your Business

The OWASP Top 10 is the closest thing the industry has to a shared language for web application risk. It is not a compliance standard and it is not a checklist for auditors — it is a ranked list of the categories of flaw that actually get organisations breached. The latest revision shifts emphasis in ways that matter for small businesses.

The Big Shifts

Insecure Design moves up

The most expensive vulnerabilities are not typos in code — they are decisions. A booking system that trusts a price sent from the browser, a password reset that emails a predictable token, an admin panel that relies on nobody guessing the URL. None of these are bugs a scanner will report; all of them are exploitable in minutes.

What to do: threat model before you build. Write down what an attacker would want, who is allowed to do what, and which values must never be trusted from the client. One afternoon of this at the start of a project is cheaper than a rewrite.

Vulnerable and Outdated Components stay near the top

Third-party code is now the majority of most applications. WordPress plugins, npm packages, PHP libraries, container base images — each one is code you did not write, running with your privileges, on your customers’ data.

What to do: keep an inventory of what you run and its versions, subscribe to advisories for the big items, and patch on a schedule rather than when something breaks. If you cannot list your dependencies today, that is the first finding.

Software and Data Integrity / supply chain

Attackers increasingly compromise the pipeline rather than the app: a hijacked package release, a malicious CI action, a script tag loaded from a domain someone let expire.

What to do: pin dependency versions and use a lockfile, restrict who can publish or deploy, enable MFA on your registry and hosting accounts, and self-host or subresource-integrity-pin third-party scripts.

Server-Side Request Forgery is now its own category

If your application fetches a URL supplied by a user — a webhook, an image importer, a link preview — it can be tricked into reaching internal systems and cloud metadata endpoints.

What to do: allowlist destinations, block private IP ranges, and never send credentials on user-influenced requests.

Broken Access Control remains the number one cause

The single most common finding in our engagements is still authorisation: changing an ID in a URL and seeing someone else’s invoice, calling an admin API as a normal user, or an object reference that is checked in the UI but not on the server.

What to do: enforce authorisation server side, on every request, per object — not per screen. Deny by default.

What This Means If You Are a South African SME

  • If you run WordPress or Shopify: your risk is overwhelmingly components and access control. Patch plugins, cut unused ones, enforce MFA on admin accounts, and restrict admin access by IP where possible.
  • If you have custom software: your risk is design and authorisation. Get a manual review; scanners do not find business logic flaws.
  • If you expose APIs: test authorisation per endpoint and per object, plus rate limiting and abuse cases.
  • If you handle personal information: these categories map directly onto POPIA’s requirement for appropriate technical safeguards. A breach caused by an unpatched plugin is difficult to defend as reasonable care.

Automated Scanning Is Necessary but Not Sufficient

Scanners are excellent at the categories that come down to known versions and missing headers. They are close to useless on design flaws and access control, because they do not know what your application is supposed to allow. That is why every AKWEBSEC engagement combines automated scanning with manual testing — the machine finds the known, the human finds the unique.
